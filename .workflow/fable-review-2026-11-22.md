# Final review 2026-11-22: Prospector dongle BLE mouse host + remap

Read-only. Heads reviewed: zmk-fork dc42f15, zmk-ble-mouse-host 79ec7d9, zmk-flask-modules b4a9531, Totem-ZMK f82267e, flask-web aac413d.
12 findings. 1-5 should be fixed before daily use. Wire format 0x2E, 0x13, 0x15 matches docs/mouse-host.md byte for byte in firmware and app (no mismatch found).

## Findings (most severe first)

1. CONFIRMED (traced into Zephyr v4.1.0+zmk-fixes smp.c; how often is a hardware question). zmk-ble-mouse-host src/ble_mouse_host.c:1350-1371 (on_security_changed) - any security error on the bonded mouse calls clear_bond(), not only "peer lost its keys". - on_connected() starts encryption at once (SMP_FLAG_ENC_PENDING). If the link drops before encryption completes (0x3E "failed to be established" in the first 6 intervals, or the mouse sleeps right then), bt_smp_disconnected() -> smp_pairing_complete(UNSPECIFIED) (smp.c:4729-4732) -> security_changed(err) (smp.c:1795) while conn is still mouse_conn -> bond and saved address deleted. There is no automatic re-pair in this fork, so the mouse is silently "not paired" at the hospital PC, where Flask is not reachable over USB. - Fix: clear only on BT_SECURITY_ERR_PIN_OR_KEY_MISSING; for every other error just disconnect and let mh_retry_work reconnect. Pre-existing upstream code, but it is the bond-loss path.

2. CONFIRMED. zmk-ble-mouse-host src/ble_mouse_host.c:949-973, 1015, 1150-1164 (first-match pairing, &mouse_pair / "Pair Mouse", 0x06 [0xFF]) - the scan has no timeout; pairing_requested is cleared only by a successful bond, unpair or pair_addr. - Press Pair Mouse with no matching mouse (or one whose Mouse appearance is only in the scan response: line 931 requires ADV_IND): the old bond is already forgotten, the dongle owns the scanner forever, so a half that sleeps (ZMK_SLEEP, 15 min) can never reconnect (split start_scanning gets -EALREADY, the fork retries every 1 s for ever), the Prospector shows the full-screen PAIR MOUSE box and input_report keeps the display awake (mouse_screen.c:92,122), and the app's Unpair button is disabled in exactly this state (mouse-tab.js:396: no bond, no address). A later app list scan also runs with first-match still armed, so the dongle can pair a device AJ did not pick. Only a reboot or &mouse_unpair ends it. - Fix: 30-60 s delayable work that clears pairing_requested and calls stop_own_scan(); enable Unpair in the app whenever state is scanning.

3. PLAUSIBLE (needs other mice in range). zmk-ble-mouse-host src/ble_mouse_host.c:931 + Totem-ZMK boards/shields/totem/totem_dongle.overlay:121-129 - this diff removed pair-name-prefix, so &mouse_pair now connects to the first ADV_IND with Mouse appearance, any RSSI, Just Works. - In the reading room a colleague's mouse advertising for reconnect can be the first match. If it accepts, the dongle bonds to it and their mouse drives AJ's workstation. If it refuses, security fails, the dongle rescans and can match it again in a loop (pairing_requested stays set). - Fix: drop the "Pair Mouse" macro on the dongle (the app list is the safe path), or require RSSI above about -50 dBm plus the timeout from 2.

4. CONFIRMED. flask-web mouse-tab.js:366-376 (pairOutcome) - a status of connecting + bonded + target address is treated as failure. - Firmware sets have_bond in on_pairing_complete, but state stays "connecting" until do_subscribes (report refs + report map read, roughly 0.2-0.7 s). A 1 s poll landing in that window shows "Pair failed, kept ELECOM..." on a pairing that succeeded, and the "Paired" toast never appears. Also wrong for a mouse whose address changes to its identity address after bonding (addr no longer equals pending.addr). - Fix: keep pending while s.addr === pending.addr and state is connecting (bonded or not); fail only when the address differs or state is idle.

5. CONFIRMED. zmk-ble-mouse-host src/ble_mouse_host.c:955-960 + flask-web mouse-tab.js:405,450 - while any half is disconnected (asleep after 15 min, or off) ZMK's split central owns the scanner, so the list scan never starts (-EALREADY, retry every 3 s). mode is still set to MH_SCAN, so status says scanning, the Prospector says "Put DEFT Pro in pairing mode", and after 15 s the app says "No mice found. Is it in pairing mode?". - AJ opens Flask from the Mac with the halves asleep, scans, and is told the mouse is the problem. The hint text explains the opposite direction (the scan blocks a half), not that a sleeping half blocks the scan. - Fix: add a status flag bit "scan waiting for the scanner" (listing && !scan_owned) and show "Wake both halves first (press a key on each)"; at least change the empty-list copy.

6. CONFIRMED. zmk-flask-modules src/flask_proto.c:523-525, 2575 - SCROLL_SETTINGS_VERSION 1 -> 2 makes every board on this branch ignore its saved drag-scroll tuning ("flask/scroll") and fall back to DT defaults. The comment says a v1 blob is a size mismatch; it is not (sizeof(flask_scroll_params) is 20 before and after, h_bias_pct sits in former padding), the version check is what drops it. - Imprint or Cyboard bumped to this pin lose saved divisors/invert once, silently. Their defaults are otherwise unchanged (h-bias-pct default 0, smooth not instantiated, ext hook weak no-op). - Fix: accept version 1, copy the params and set h_bias_pct from the live DT default.

7. CONFIRMED (low odds). zmk-ble-mouse-host src/ble_mouse_host.c:256,272 - emit_motion sets prev_buttons = buttons even when input_report_key timed out after 10 ms. - If the input thread is stalled longer than that (it sends HID inline; a suspended USB host blocks it up to 30 ms per report), a dropped release leaves the key position held: stuck click, or stuck &mo L_DRAG_SCROLL, until that same button is pressed again. Totem-ZMK src/mouse_host/mouse_keys.c:75 has the same shape (drop is only logged). - Fix: fold a bit into prev_buttons only when its input_report_key returned 0, so the next report retries it.

8. CONFIRMED against the spec. zmk-ble-mouse-host src/ble_mouse_host.c:1396 vs 739-750 - on_pairing_complete unpairs the previous mouse before HID discovery has finished. - Pick a listed device that pairs but has no usable HID service: by then have_target is false, disc_service_cb calls clear_bond(), and both the new and the old mouse are gone (state idle). docs/mouse-host.md 0x06 says the old mouse comes back. - Fix: keep have_prev until do_subscribes(), unpair the old bond there.

9. CONFIRMED (needs a double click or an armed first-match scan). zmk-ble-mouse-host src/ble_mouse_host.c:1282-1295, 951-953 - scan_start clears the list but does not restart a scan it already owns; the controller's duplicate filter then never re-reports devices it already delivered. - Second Scan click before the first poll returns, or a list scan started while &mouse_pair is scanning: the list stays empty for the 15 s. - Fix: in scan_start, stop_own_scan() first when scan_owned.

10. CONFIRMED (rare). zmk-ble-mouse-host src/ble_mouse_host.c:1309-1343 - pair_addr with the address of the currently bonded mouse keeps the old keys as "prev". - If the mouse erased its side: security fails, target_failed restores the stale bond, the next reconnect fails again and clear_bond leaves nothing paired; a second Pair is needed. If the mouse kept its keys: it connects with no pairing_complete, so the status never shows bonded until the next reconnect cycle. - Fix: when the target equals mouse_addr, bt_unpair it first and treat it as a fresh pairing.

11. CONFIRMED (traffic only). Totem-ZMK totem_dongle.overlay:177-181 with zmk app/src/pointing/input_listener.c:224-236, 302-310 - with process-next, flask_scroll's STOP is ignored and the zeroed X/Y run the base chain, so each mouse report during drag scroll also sends a zero-movement HID mouse report. - Roughly doubles HID reports while drag scrolling (BLE host link shares airtime with the mouse, two halves and maybe a phone). No wrong output. - Fix if scroll stutters on hardware: have mouse_keys run inside the drag_scroll override and drop process-next, or skip zero REL values in a tiny processor.

12. PLAUSIBLE / copy. (a) Totem-ZMK config/totem.keymap MOUSE_KEYS rows: Function and Mouse bind the buttons outright, so a button rebound on Base in the Keymap tab (for example to Hold layer Drag Scroll) is still MB4 etc. on those two layers; the card text (mouse-tab.js:443) does not say so. (b) Replacing a mouse needs one spare bond: BT_MAX_PAIRED=10 = 2 halves + mouse + up to 4 hosts + 2 phones is 9, the transient second mouse bond makes 10; anything more and Pair fails with "kept old". (c) mouse-tab.js:396 Unpair disabled while a first-match scan runs (see 2).

Checked, no finding: 8-button HID descriptor (same report size, USB still keyboard/mouse HID only, no diff touches USB interfaces or the CDC disable); split scan retry (is_scanning cleared, retry rechecks is_enabled and slots); 0x2E buffer bounds (name chunks 27/26, pair len check, index checks); autoexit with mouse keys and &mo / &tog L_DRAG_SCROLL (held vs latched traced, disconnect releases through release_work); hold-tap slot renumber (per-slot settings keyed by index, reset is documented); static RAM (CI: dongle 232622 B / 256 KB = 88.7 %, sysworkq stack 4096, new work items add no thread); halves' images (same size before/after per CI).
